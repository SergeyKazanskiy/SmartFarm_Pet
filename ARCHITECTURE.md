# Smart Farm — Architecture Guide

> Краткое руководство по организации исходного кода проекта.

## 1. Основные принципы

Проект построен на Next.js, React и TypeScript.

Главный принцип организации — **Feature-Based Architecture**: каждая функциональная область приложения по возможности автономна.

Основные правила:

1. `app/` отвечает за маршрутизацию и сборку страниц.
2. `features/` содержит функциональность приложения.
3. `components/` содержит универсальные UI-компоненты.
4. `api/` отвечает за подключение к внешним сервисам.
5. `stores/` содержит глобальное состояние приложения.
6. `settings/` содержит статические настройки и значения по умолчанию.
7. Общие функции, типы и хуки размещаются в соответствующих общих папках.

Не создавать абстракции и дополнительные уровни вложенности без реальной необходимости.

## 2. Структура проекта

```text
src/
├── api/            # Подключения к внешним сервисам
├── app/            # Маршруты, страницы и layouts Next.js
├── assets/         # Локальные ресурсы приложения
├── components/     # Универсальные UI-компоненты
├── features/       # Функциональные модули приложения
├── hooks/          # Общие React-хуки
├── locales/        # Переводы и i18n
├── settings/       # Конфигурация и настройки
├── stores/         # Глобальное состояние Zustand
├── styles/         # Глобальные стили и дизайн-токены
├── types/          # Общие TypeScript-типы
└── utils/          # Вспомогательные функции

public/             # Публичные статические ресурсы
```

### Назначение папок

| Папка | Назначение |
|---|---|
| `api` | Supabase, FastAPI, HTTP-клиенты |
| `app` | Страницы, layouts, route handlers |
| `assets` | Шрифты, звуки, SVG |
| `components` | Button, Input, Dialog, Sidebar |
| `features` | Explorer, Editor, Projects и другие модули |
| `hooks` | Общие React-хуки |
| `locales` | Переводы RU/EN |
| `settings` | Константы, конфигурации, defaults |
| `stores` | Глобальные Zustand-сторы |
| `styles` | CSS, OKLCH-токены |
| `types` | Общие типы и контракты |
| `utils` | Форматтеры, хелперы |

## 3. Правила организации Features

Каждая функциональность приложения размещается в отдельной папке `features/`.

Пример:

```text
features/
├── projects/
├── explorer/
├── editor/
├── properties/
└── modals/
```

При необходимости внутри функционального модуля создаются:

```text
explorer/
├── components/     # Компоненты Explorer
├── hooks/          # Хуки Explorer
├── services/       # Запросы и операции с данными
├── stores/         # Локальное состояние Explorer
├── types/          # Типы Explorer
└── index.ts        # Публичный интерфейс модуля
```

Необязательно создавать все подпапки заранее.

### Правило размещения

- Используется только в одном модуле → хранить внутри этого модуля.
- Используется в нескольких независимых модулях → рассмотреть перенос в общую папку.
- Является универсальным UI-элементом → `components/`.
- Содержит бизнес-функциональность → `features/`.

## 4. API и работа с данными

Внешние подключения находятся в `api/`.

```text
api/
├── supabase/
│   ├── client.ts
│   └── server.ts
├── fastapi/
│   └── client.ts
└── http/
    └── fetcher.ts
```

Правила:

- `client.ts` — подключение, используемое в браузере.
- `server.ts` — серверное подключение Supabase.
- `fastapi/client.ts` — общий HTTP-клиент FastAPI.
- Конкретные запросы хранятся в `features/*/services/`.

Например:

`features/explorer/services/explorer.service.ts`

Здесь находятся операции получения дерева проекта, папок, файлов и дисциплин.

Не размещать бизнес-логику непосредственно в компонентах React.

---

## 5. Управление состоянием

Используется Zustand.

Общее состояние приложения:

```text
stores/
├── auth.store.ts
├── theme.store.ts
└── app.store.ts
```

Локальное состояние функциональных модулей:

```text
features/
├── explorer/
│   └── stores/
│       └── explorer.store.ts
└── editor/
    └── stores/
        └── editor.store.ts
```

Правила:

- `settings/` — начальные и статические значения.
- `stores/` — изменяемое состояние приложения.
- `features/*/stores/` — состояние конкретного функционального модуля.

Не создавать Zustand-store для каждого небольшого компонента.

---

## 6. Типы и контракты

Общие типы:

```text
types/
├── database.types.ts
├── api.types.ts
└── common.types.ts
```

Типы конкретных модулей хранятся внутри соответствующих `features`.

Например:

`features/explorer/types/explorer.types.ts`

Типы базы данных Supabase желательно генерировать автоматически.

Не дублировать одинаковые интерфейсы в разных модулях.

---

## 7. Стили и оформление

Используется Tailwind CSS v4.

```text
styles/
└── tokens.css

app/
└── globals.css
```

Правила:

- `globals.css` — глобальные стили и подключение CSS.
- `tokens.css` — CSS-переменные и дизайн-токены.
- Цветовая система строится на OKLCH.
- Компоненты используют Tailwind-классы.
- Общая функция `cn()` находится в `utils/cn.ts`.

Не создавать отдельные CSS-файлы для каждого компонента без необходимости.

## 8. Правила именования

| Элемент | Стиль | Пример |
|---|---|---|
| React-компоненты | PascalCase | `ExplorerTree.tsx` |
| React-хуки | camelCase с use | `useExplorer.ts` |
| Zustand-store | kebab-case + store | `explorer.store.ts` |
| Сервисы | kebab-case + service | `explorer.service.ts` |
| Типы | kebab-case + types | `explorer.types.ts` |
| Утилиты | camelCase | `formatDate.ts` |
| Конфигурации | kebab-case + config | `app.config.ts` |

## 9. Правила зависимостей

Предпочтительное направление:

```text
app
 └── features
      ├── components
      ├── api
      ├── hooks
      ├── stores
      ├── types
      └── utils
```

Общие папки (`components`, `hooks`, `stores`, `types`, `utils`, `settings`) могут использоваться функциональными модулями.

Правила:

1. `components/` не должен зависеть от `features/`.
2. Один функциональный модуль не должен напрямую изменять внутреннее состояние другого модуля.
3. Взаимодействие между модулями организуется через публичные интерфейсы, сервисы или общие контракты.
4. Не допускать циклических импортов.
5. Не смешивать серверный и клиентский код.

---

## 10. Общие правила разработки

- Использовать TypeScript.
- Не дублировать код без необходимости.
- Предпочитать простые решения сложным абстракциям.
- Не создавать файлы и папки заранее без необходимости.
- Разделять UI, работу с данными и бизнес-логику.
- Не переносить функциональность в общие папки только ради повторного использования.
- Сохранять существующую архитектуру при добавлении новых функций.
- Перед введением нового архитектурного решения обновлять этот документ.
